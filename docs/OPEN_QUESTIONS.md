## A. 바로 정해야 하는 것 (동작에 영향 큼)

### A1. 모집 마감이 지났는데 인원이 다 안 찬 공구 (DB.md 8.1 보류 항목)

- **현재 구현**: 마감이 지나면 **참여만 막히고**(`POST409`), 게시글은 `RECRUITING`으로 남습니다. 자동 취소·환급이 없습니다.
  - 목록의 `모집중만 보기`에 마감 지난 글이 계속 보입니다 (`마감임박순` 정렬에서만 빠짐)
  - 호스트·참여자의 포인트가 계속 보류된 채로 남습니다. 호스트가 직접 취소해야 환급됩니다
- **선택지**
  1. ⭐ 마감 시각에 스케줄러가 자동 취소 + 전원 환급 (호스트 포함). 자동 수령 스케줄러와 같은 방식으로 바로 만들 수 있음
  2. 마감 후 호스트에게 "남은 단위를 본인이 떠안고 진행 / 취소" 선택권을 줌 (UI·API 추가 필요)
  3. 지금처럼 두고 목록에서만 마감 지난 글을 숨김

### A2. 모집완료 후 호스트가 영수증을 안 올리는 경우

- **현재 구현**: 기한이 없습니다. 모집완료 상태에서는 참여자가 **참여 취소(환급)할 수 있어서** 참여자는 빠져나올 수 있습니다. 호스트 패널티는 없습니다
- **선택지**
  1. 모집완료 후 N시간(예: 48시간) 안에 영수증을 안 올리면 자동 취소 + 전원 환급
  2. 1 + 호스트 보류 포인트를 참여자에게 나눠 주는 패널티 (회의록 10/27 안, D8의 보증금 목적)
  3. 지금처럼 둠

### A3. 문의중인 참여자가 있을 때 정산 (D10 남은 미정)

- **현재 구현**: 문의중(`INQUIRING`)인 사람이 한 명이라도 있으면 **공구 전체 정산이 운영팀 처리 전까지 멈춥니다**. 자동 수령 처리도 문의중인 사람은 건드리지 않습니다
- **선택지**
  1. 지금처럼 전체 보류 (단순, 호스트 정산이 늦어질 수 있음)
  2. 문의중인 사람 몫만 남기고 나머지는 먼저 정산 (포인트 담당 쪽에 "일부 정산" 기능 필요)

### A4. 단위 가격이 나누어떨어지지 않는 경우 (예: 10,000원 / 3단위)

- **현재 구현**: 공구 등록을 거부합니다 (`POST4003`)
- **선택지**
  1. 지금처럼 거부 (호스트가 가격을 맞춰 입력)
  2. 단위 가격은 내림, 나머지는 호스트가 부담 (영수증 차액 정산의 나머지 처리와 같은 방식)
  3. 단위 가격은 올림, 남는 금액은 정산 때 환급

## C. 운영팀·관리자 기능

관리자 화면은 나중에 추가하기로 했습니다 (D10). 그런데 **화면이 없으면 아래 일을 처리할 방법이 없습니다.**

### C1. 수령 문의 처리 (가장 급함)

- 문의가 들어오면 그 공구는 정산이 멈춥니다 (A3). 운영팀이 처리해야 풀립니다
- 처리하려면 DB만 바꾸면 안 되고, **포인트 환불(부분·전액)과 정산 재개**가 함께 일어나야 합니다
- **필요한 것**: 최소한 관리자용 API 1개 — `POST /api/admin/inquiries/{id}/resolve` (결과·환불 금액·메모 → 환불 처리 → 참여자 `RECEIVED` → 전원 받았으면 정산)
- **결정 필요**: 관리자 API를 MVP에 넣을지, 관리자 계정(`users.role = ADMIN`)은 어떻게 만들지 (DB 직접 수정?)

### C2. 신고 처리

- 지금은 `PENDING`으로 저장만 됩니다. 확인·처리 방법이 없습니다
- 같은 사람을 같은 이유로 여러 번 신고해도 모두 저장됩니다 (중복 방지 없음). 막을지 결정 필요

### C3. 계정 정지 (D9)

- 미수금 기한 초과 10회 정지는 포인트 담당 쪽 스케줄러에서 `users.status = SUSPENDED`를 바꿔야 합니다
- 정지 기간(`suspended_until`)이 없으면 무기한 정지로 처리하게 해뒀습니다 (`User.isSuspended`)
- 정지된 사람이 이미 가진 Access Token은 최대 30분 더 쓸 수 있습니다. 바로 막으려면 요청마다 DB 조회가 필요합니다

## D. 포인트·채팅 담당 팀원과 맞출 것

공구 기능이 포인트·채팅을 부르는 창구를 인터페이스로 만들고, 지금은 **가짜 구현(Fake)**으로 돌아갑니다.

| 인터페이스 | 위치 | 가짜 구현의 동작 |
|---|---|---|
| `PointClient` | `integration/point/` | 결제는 항상 성공, 잔액은 0, 미수금 없음 |
| `ChatClient` | `integration/chat/` | 아무것도 안 함, 채팅방 ID는 `null` |

### D1. 담당자가 할 일

1. `PointClient` / `ChatClient`를 구현한 클래스를 `@Component`로 만든다
2. `FakePointClient` / `FakeChatClient`를 지운다 (같은 타입 빈이 두 개면 앱이 안 뜸)
3. 각 메서드 주석에 적힌 규칙을 지킨다
   - **호출한 쪽 트랜잭션 안에서 실행** (전파 REQUIRED). 실패하면 `GeneralException`을 던져 전체 롤백
   - **락 순서**: 공구 쪽이 게시글 행 락을 먼저 잡고 부른다. 지갑 락은 그다음 (D4)
   - 잔액 부족 `POINT409`, 미수금 `POINT4031`, 동시 변경 충돌 `POINT4091` (에러 코드는 이미 `ErrorStatus`에 있음)

### D2. 지금 가짜 값이라 화면에 영향 있는 것

- 공구 등록·참여 응답의 `balanceAfter`가 항상 0
- 공구 상세·참여 응답의 `chatRoomId`가 항상 `null`
- 내 정보의 포인트가 항상 0, `restricted`가 항상 `false`
- 주문 조회의 `heldPoint`는 포인트 기능 대신 참여 정보로 계산 중 (연동 후 포인트 쪽 값으로 바꿀지 결정)

### D3. 인터페이스에 없지만 필요할 수 있는 것

- 미수금이 납부됐을 때 호스트에게 추가 지급하는 건 포인트 쪽 내부 처리로 가정했습니다 (D9)
- 수령 문의 환불(C1)용 메서드 (`refundPartially` 등)는 관리자 기능을 만들 때 추가 필요

## E. 실행 환경

### E1. DB 테이블 생성 방식

- **현재**: `application.yaml`에 `ddl-auto` 설정이 없어서 **앱을 띄워도 테이블이 생기지 않습니다** (예전에 설정 파일 변경을 빼달라고 하셔서 넣지 않았음)
- 테스트는 H2 메모리 DB에 자동 생성되므로 영향 없음
- **선택지**
  1. ⭐ 개발 중엔 `spring.jpa.hibernate.ddl-auto: update`를 `application.yaml`에 추가 (간단)
  2. Flyway로 SQL 마이그레이션 파일 관리 (배포 전엔 결국 필요)

### E2. Docker

- 나중에 하기로 했습니다. 앱 실행에는 PostgreSQL·Redis가 필요하고, `Web/.env`에 `JWT_SECRET`가 있어야 합니다

### E3. 서버 여러 대

- 자동 수령 스케줄러는 서버 1대 기준입니다. 여러 대로 늘리면 중복 실행을 막는 장치(ShedLock 등)가 필요합니다

## F. 작은 결정 (지금 구현으로 둬도 무방)

| 항목 | 현재 구현 | 다른 선택지 |
|---|---|---|
| 참여 취소 후 같은 공구에 다시 참여 | 허용 (기존 참여 행을 다시 씀) | 재참여 금지 |
| 차단했는데 이미 같은 공구에 함께 있음 | 그 공구는 그대로 진행 | 차단 시 공구에서 빠지게 |
| 공구 상세 조회수 | 볼 때마다 +1 (같은 사람 반복 포함) | 사람당 하루 1회 |
| Refresh Token | 사용자당 1개 (다른 기기에서 로그인하면 이전 기기는 재로그인) | 기기별 여러 개 |
| 공구 수정 시 가격·단위 | 수정 불가, 보내도 무시 (D8) | 보내면 400 에러 |
| 후기 삭제 | 삭제 API 없음 | 삭제 허용 |
| 학교명 (`universityName`) | 비어 있음 (이메일 도메인 → 학교명 표가 없음) | 도메인 표 작성 |
| 고아 이미지 (업로드만 하고 안 쓴 파일) | 정리 안 함 | 주기적 삭제 |
| 내 공구함 | 전체를 불러와 메모리에서 필터·페이지 처리 (공구 수가 많아지면 느려짐) | DB 쿼리로 변경 |
| 유저 프로필 최근 거래 | 진행 중인 공구도 포함 | 정산완료만 |

## G. 2026-11-16 요구사항 변경으로 새로 생긴 질문

### G1. 마감이 지난 뒤 장소 의견 불일치로 빈자리가 생기는 경우
- 모집완료(`RECRUITED`)에서 누가 나가면 `RECRUITING`으로 돌아가는데, 이미 `deadline_at`이 지났으면 새로 참여할 수 없다
- 지금 구현: 그대로 둔다 (호스트가 취소하거나, 마감을 연장하는 기능이 있어야 함). A1(인원 미달 마감)과 같이 정하면 됨
- 선택지: 빈자리가 생기면 마감을 N시간 자동 연장 / 호스트가 마감 연장 / 남은 인원으로 진행(단위 재분배)

### G2. 장소 합의가 끝나지 않는 경우
- 일부 참여자가 동의도 나가기도 안 하면 주문이 막힌다
- 선택지: 제안 후 N시간 안에 응답 없으면 동의로 간주 / 호스트가 미응답자를 내보내기(환급)

### G3. 미수금 기능 정리 (D21)
- 차액 정산이 없어져 미수금이 생길 곳이 없다. `PointClient.validateNoUnpaidDebt`, `hasUnpaidDebt`, `PAY_DEBT`, `users.overdue_count`, `point_debts`를 포인트 담당과 정리해서 지울지 결정 필요

### G4. 기존 데이터 마이그레이션
- 컬럼 변경: `users.login_id` 삭제, `posts.trade_*` → `host_latitude/longitude`·`distribution_place_*`·`search_words`·`title_chosung`, `orders.receipt_amount` 삭제, `participations.adjustment_*` → `place_agreed`·`leave_reason`·`left_at`
- 아직 운영 데이터가 없다면 DB를 새로 만들면 된다. 데이터가 있으면 `search_words`·`title_chosung` 일괄 채우기가 필요 (E1과 같이 결정)

### G5. 위치 역산 방지 수준
- 응답에는 거리 구간만 주지만, 반경 500m·1km 필터를 위치를 바꿔 가며 반복 호출하면 대략적인 위치는 좁혀질 수 있다
- 필요하면: 집 위치 변경 횟수 제한(예: 하루 N번), 글에 저장하는 좌표를 약간 흐리게(예: 100m 격자) 저장
